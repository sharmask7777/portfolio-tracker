# Concepts

> Shared domain vocabulary for this project — entities, named processes, and status concepts with project-specific meaning. Seeded with core domain vocabulary, then accretes as ce-compound captures and refreshes learnings; direct edits are fine. Glossary only, not a spec or catch-all.

## Core Entities & Holdings

### Portfolio
An investor-scoped container that aggregates investments across multiple asset classes and folios into a unified tracking and valuation boundary.
*Avoid: Account, bucket*

A Portfolio owns multiple Folios and manual assets, but does not directly own Transactions. Historical valuation snapshots are calculated and recorded at the Portfolio boundary.

### Folio
An account registered with an Asset Management Company (AMC) holding mutual fund units under a specific tax-identity profile.
*Avoid: Fund account, sub-account*

A Folio holds units of a single mutual fund scheme within a Portfolio and maintains a strictly chronological ledger of Transactions.

### Transaction
An immutable financial record representing a unit or cash modification within a Folio, such as a purchase, systematic investment plan installment, redemption, or switch.
*Avoid: Ledger entry, trade*

Every Transaction carries a date, type, unit change, amount, and resulting Running Balance.

### Running Balance
The cumulative quantity of unsold units remaining in a Folio immediately following the execution of a Transaction.
*Avoid: Current units, balance units*

The Running Balance advances with purchases and decreases with redemptions. It serves as the authoritative ground truth for chronological sequencing on dates with multiple same-day transactions.

## Ingestion & Ledger Lifecycle

### CAS (Consolidated Account Statement)
A consolidated financial statement generated by registrars or depositories representing the authoritative, cumulative transaction history of an investor's holdings from inception.
*Avoid: Statement, monthly report*

Because a CAS contains the complete transaction history since portfolio inception, ingestion uses Clean-Slate Reconstruction rather than append-only updates.

### Clean-Slate Reconstruction
An ingestion protocol where all pre-existing ledger entries and cached valuation checkpoints for a touched Folio are cleared before streaming authoritative records from a cumulative statement.
*Avoid: Purge and reload, full reset*

Clean-Slate Reconstruction ensures complete state predictability across heterogeneous deployments, preventing orphaned duplicate records or historical sign anomalies from persisting.

## Valuation & Performance

### XIRR (Extended Internal Rate of Return)
The annualized internal rate of return calculated from an irregular schedule of cash inflows, cash outflows, and terminal portfolio valuation using polynomial root-finding.
*Avoid: CAGR, absolute return*

XIRR treats purchases as capital outflows and redemptions along with terminal valuation as capital inflows. Duplicate or misplaced redemption entries artificially magnify early capital inflows, causing root-finding solvers to converge on severely distorted return figures.

## Mobile & Distributed Client Concepts

### Active Portfolio Scope
The active viewing boundary determining whether portfolio metrics, valuation cards, and asset lists reflect the aggregated family corpus (`consolidated`) or are filtered strictly to a single tax-identity profile (`member`).
*Avoid: Active profile, selected account*

Under Active Portfolio Scope, selection state is managed uniformly across client platforms and persisted via platform-specific storage adapters. In consolidated scope, member PAN badges reflect percentage corpus contributions derived from backend PAN breakdowns; in member scope, positions and realized gain schedules isolate to the selected member.

### Decoupled Daily Valuation
A client-side evaluation pattern where a mobile or edge client recomputes asset valuations and day's returns directly from public financial feeds without requiring an active network connection to the self-hosted portfolio server.
*Avoid: Remote valuation sync, server-dependent price refresh*

Under Decoupled Daily Valuation, the mobile client holds immutable unit holdings in local SQLite storage and queries public market feeds (e.g. AMFI NAV API) to calculate `units * current_nav`, preserving offline visibility while keeping heavy historical computations anchored to the server.

### Outbox Sync Queue
A reliable, local-first transaction pattern where file uploads (such as CAS statement PDFs) and their encrypted access credentials are staged locally in an offline-durable database table before streaming to the server.
*Avoid: Direct background upload, unbuffered file post*

When the remote server is unreachable, the Outbox Sync Queue buffers statements with a `PENDING` status and auto-increments retry counts upon transient failures, guaranteeing zero lost user submissions during network transitions.

### Hardware Biometric Pairing
A two-tier authentication architecture combining short-lived, single-use cryptographically random pairing tokens (exchanged via visual QR code scanning) with long-lived device credentials stored in OS-level hardware keystores (iOS Keychain / Android KeyStore) gated by local biometric authentication.
*Avoid: Plaintext token storage, password re-entry*

Hardware Biometric Pairing allows seamless, passwordless app unlock on mobile clients while supporting self-hosted instances deployed on arbitrary local network IPs or hostnames.

### Analytics SSoT Synchronization
The synchronization pattern where derived cross-fund analytics (such as company exposures, sector allocations, and stock overlap) are computed exclusively by the backend domain engine (`/api/portfolio/:id/exposures`, `/api/portfolio/:id/xray`) and persisted in local client storage, avoiding client-side approximation drift.
*Avoid: Client blueprint calculation, local mock exposure*

Analytics SSoT Synchronization guarantees that portfolio look-through metrics remain numerically identical across web and mobile surfaces while preserving offline caching.

### Multimodal Visual Verification Loop
The autonomous verification pattern where agents capture actual UI rendering screenshots from emulators or browsers during test runs and perform multimodal visual analysis to check for layout clipping, contrast, typography, and responsive padding before signing off on a change.
*Avoid: Headless-only assertion, blind DOM check*

The Multimodal Visual Verification Loop prevents silent visual regressions that pass headless unit tests from reaching production.

### Withdrawal Simulation
A predictive tax and exit load calculation for redeeming units from a specific folio or hypothetical position, evaluating FIFO lot exhaustion, grandfathered deemed cost under Section 55(2)(ac), statutory tax liability under Sections 112A, 111A, or 50AA, exit load penalties, and net in-hand proceeds.
*Avoid: Sell calculator, mock redemption*

Under Withdrawal Simulation, the client uses backend calculation as the single source of truth (`POST /api/tax/simulate-sell`) to guarantee cross-platform numerical parity, with transparent offline fallback to local calculations when unreachable.
